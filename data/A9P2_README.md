# A9P2 - Continuous Performance Profiling in Mobile CI/CD Pipelines for Early Detection of Application Performance Regressions

**Track:** Track 1  
**Application:** Smart-grid consumer energy monitoring app

This dataset is synthetic, generated by gen_author9.py with seed 2118. It must be described as synthetic in any publication.

## Simulated scenario

A utility's consumer app shows smart-meter consumption charts, bills, outage maps and demand-response opt-ins. Each CI run profiles one commit on one device class and scenario, recording code-change features, static-analysis flags, data volume rendered (interval readings) and performance metrics. The label marks commits later confirmed as true performance regressions (~9%).

## How it was generated

A hidden regression latent depends on change size, main-thread I/O, chart-library upgrades x chart scenario, new dependencies, UI x dashboard, DB x cold start. Regressions add 12-60% to latency and raise jank/frame time/memory. Latency also depends on device speed, scenario, log(meter points) and a slow upward drift over time, with 12% noise, so a naive threshold on latency or delta vs baseline is noisy.

Realism noise common to all numeric signals: ~5% multiplicative Gaussian measurement noise, 1-3% missing values in a few columns (empty cells), and ~0.5-1% injected outliers (listed per table below). Targets were computed from the noise-free latent signals, so the observed features are imperfect proxies.

## Suggested experiments

1. Regression detection from metrics: delta vs baseline threshold (naive) vs GBM / change-point methods; report F1, PR-AUC, detection delay.
2. Pre-merge risk prediction using only code-change features (no runtime metrics); report PR-AUC to decide which commits to profile.
3. Latency prediction (R^2, MAPE) per device class to set adaptive budgets.
4. Profiling budget study: profile only top-k risky commits; recall of regressions vs device-farm minutes.
